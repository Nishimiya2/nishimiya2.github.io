1. 引言：嵌入式并发安全的特殊性

在服务器端Java或C++开发中，并发问题通常由操作系统线程调度引起，有完善的内存模型（如JMM）兜底。但在嵌入式C语言裸机或RTOS环境中，我们直面的是物理寄存器、CPU流水线、多级缓存（Cache）和硬件中断。

嵌入式并发Bug的杀伤力极大：

  • 导致 HardFault硬错误（程序直接跑飞）。
  • 引发 外设初始化失败（设备间歇性失灵）。
  • 造成 内存撕裂（DMA传输半成品数据）。
  • 严重的 优先级反转 可能导致系统任务全面饿死（参考1997年火星探路者事故）。

本白皮书从 硬件根源 → 三大核心语义 → 典型灾难案例 → 防御矩阵 → 调试工具 五个维度，构建完整的嵌入式并发知识体系。

2. 嵌入式并发问题的三大硬件根源

理解编程语义之前，必须理解CPU硬件为了“快”而做出的三种妥协，这是所有并发Bug的物理源头。

2.1 根源一：中断/任务抢占（时间维度的撕裂）

  • 现象
    CPU采用时间片轮转（RTOS）或中断优先级抢占。一个32位甚至64位的全局变量修改，在汇编层面对应多条指令（如 LDR 加载，ADD 加1，STR 回写）。

  • 后果
    当主循环执行到一半时，高优先级中断触发，修改了同一块内存区域。当中断返回时，主循环继续基于“半成品”数据运算，产生不可预知的撕裂值。

  • 嵌入式特质
    单核CPU同样存在此问题，因为中断是异步的。

2.2 根源二：编译器优化与寄存器缓存（编译器层面的近视）

  • 现象
    开启 -O2 / -O3 优化后，编译器为了效率，将频繁访问的全局变量加载到CPU的通用寄存器（R0-R12）中。

  • 后果
    此后CPU不再去物理内存地址取值，而是直接使用寄存器中的备份。当中断服务函数（ISR）修改了内存中的变量，主循环因持有寄存器旧值而永远感知不到变化，导致死循环或逻辑错误。

  • 嵌入式特质
    这与Java的JIT编译不同，C语言中完全由 volatile 关键字控制。

2.3 根源三：CPU流水线与写缓冲（执行顺序的重排）

  • 现象
    现代高性能Cortex-M7/M33及多核A系列芯片，为了填充分支预测的空闲周期，支持 指令重排序；同时为了减少总线等待，引入了 Store Buffer（写缓冲）。

  • 后果
    代码明明先写了寄存器A，后写了寄存器B，物理上却可能先执行了B的写操作。如果A是开启外设时钟，B是配置外设模式，就会导致外设时钟未稳时寄存器配置无效。

  • 嵌入式特质
    需要内存屏障指令（DMB / DSB）强制串行化。

3. 三大核心并发语义深度剖析（嵌入式视角）

本章详细拆解 原子性、可见性、有序性，它们是衡量代码安全性的标尺。

3.1 原子性（Atomicity）：操作不可分割

定义

一组操作要么全部执行完毕且不被任何外部事件（中断或其它核心）打断，要么完全不执行。不存在“执行到一半”的中间状态。

嵌入式破坏场景

  1. 非对齐访问
    ARM Cortex-M 要求4字节对齐的 uint32_t 写入。如果变量未对齐，一次赋值会被拆分成多次字节写入，中断恰好发生在两次字节写入之间，读到的值是混合的垃圾数据。

  2. 64位变量操作
    在32位Cortex-M3/M4上，操作 uint64_t 需要2条 LDRD / STRD 指令。中断打断第一条指令后，高32位和低32位分别来自新旧两个不同的时间点。

  3. 读-改-写（Read-Modify-Write）
    如 flag |= BIT_MASK，本质是读内存、或运算、写内存三步。中断在写回前修改了 flag 的其他位，主循环写回时会 覆盖 中断的修改，造成位标志丢失。

C语言语义保证

场景 保证手段 说明
单核裸机 __disable_irq() / __enable_irq() 包裹临界区，禁止中断抢占
多核/带Cache ldrex / strex 独占指令 实现无锁原子操作，或使用芯片硬件信号量

3.2 可见性（Visibility）：修改立即生效

定义

一个执行单元（任务/中断/核心）对共享变量做出的修改，必须能够被其他执行单元 立即 观察到。

嵌入式破坏场景

  1. 编译器的寄存器提升（Register Promotion）
    局部优化导致变量常驻寄存器，ISR修改的内存值被忽略（经典死循环）。

  2. 多核Cache不一致性
    双核（如ESP32或Cortex-A9）各有独立的L1 Data Cache。Core0修改了变量（仅写入L1 Cache，尚未写回主存SDRAM），Core1读取该变量时，因Cache Miss而从主存拿旧值，拿到的是脏数据。

C语言语义保证

场景 保证手段 说明
单核 volatile 关键字 强制编译器放弃寄存器优化，每次从绝对物理地址读取
多核 volatile + Cache同步 修改后调用 SCU_CleanInvalidateDCache，或用 Non-Cacheable 属性定义共享内存

3.3 有序性（Ordering）：遵循程序逻辑顺序

定义

程序最终执行的物理顺序，应当与源代码的编写逻辑顺序保持一致性（在依赖关系成立的场景下）。

嵌入式破坏场景

  1. 外设初始化失效（经典M7坑）
    先开时钟，再改模式。CPU重排后先改模式，因时钟未开导致写入无效。

  2. DMA缓冲区就绪标志提前设置
    CPU在数据尚未完全从Cache刷新到主存前，就置位了DMA启动标志。DMA从主存搬运旧数据，导致传输内容错误。

C语言语义保证

屏障类型 指令 作用
编译器屏障 asm volatile("" ::: "memory") 阻止编译器优化重排，不阻止CPU硬件重排
数据内存屏障 __DMB() 屏障前的内存访问在屏障后的内存访问之前完成（多核共享）
数据同步屏障 __DSB() 等待所有流水线内存访问完成（外设寄存器配置）
指令同步屏障 __ISB() 冲刷指令流水线（跳转或页表修改）

4. 嵌入式C四大典型灾难场景全还原

4.1 原子性灾难：64位时间戳撕裂

场景描述

高精度任务获取系统运行时间。

uint64_t volatile g_sys_tick = 0; // 假设未使用关中断保护

// 1ms 滴答中断
void SysTick_ISR(void) {
    g_sys_tick++; 
    // 汇编: 1. LDRD R0,R1,[addr]  (加载高32位到R1,低32位到R0)
    //       2. ADDS R0,#1
    //       3. ADCS R1,#0
    //       4. STRD R0,R1,[addr]  (写回)
}

// 应用任务
void task(void) {
    uint64_t start = g_sys_tick; 
    // 如果读取时恰好停在 [加载完高32位] [加载低32位] 之间，且中断更新了数值，
    // start 的高32位是新值，低32位是旧值，计算出的时间完全是错误的。
}
